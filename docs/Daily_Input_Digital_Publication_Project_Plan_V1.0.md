- **整理日期：** 2026-11-06

- **视觉主题：** Lilac Moon（月辉紫白）V1.0

## 1. 项目目标与总体原则

本项目不是简单地把日报从 PDF 转换成 HTML，而是建立一条完整的数字出版流水线：

1. LLM 负责研究、资料筛选、分析和 Markdown 正文生产。
2. Markdown 是内容源文件，便于编辑、保存、归档和重新出版。
3. 云端出版引擎负责解析 Markdown、处理媒体资源、套用固定 HTML/CSS 模板并生成最终文件。
4. 自动质检负责验证内容、结构、媒体、链接和实际浏览器显示。
5. Gmail 负责将最终 HTML 作为附件发送。
6. 正常情况下，用户无需每天打开电脑、运行命令、复制内容或手动发送邮件。

### 1.1 核心原则

- **低摩擦优先：** 每天无需用户参与生产过程；异常时主动通知。
- **职责分离：** LLM 不负责最终排版；出版引擎不负责写作判断。
- **内容与呈现分离：** Markdown 保存内容，HTML/CSS 负责呈现。
- **确定性优先：** 能由普通程序稳定完成的工作，不交给 LLM 临场决定。
- **可恢复：** 每个阶段有独立状态、日志和重试策略。
- **不重复生产：** 同一日期、版本和输入复用已生成的成品。投递结果不明时允许带说明补发一次。
- **不静默失败：** 未通过质量检查的日报不得冒充成功成品。
- **可迁移：** 将来更换 LLM 供应商，不应迫使出版引擎和内容协议推倒重来。

第一版不开发：
- 折叠式抽屉目录。
- 字体大小调整控件。
- 阅读进度记忆。
- 收藏、笔记和批注。

## 3. 总体技术架构

### 3.1 目标架构

```text
Cloud Scheduler
      |
      v
Cloud Run Job / Python Orchestrator
      |
      +--> OpenAI API
      |      +--> 研究与资料检索
      |      +--> 选题与历史去重
      |      +--> Markdown 正文生成
      |      +--> 内容修订与核验
      |
      v
Markdown + manifest + media assets
      |
      v
Content Validation
      |
      v
Python Publication Engine
      +--> Markdown Parser
      +--> HTML Template / CSS
      +--> Image Processor
      +--> Link / Anchor Generator
      +--> Single-file Packager
      |
      v
Browser QA (Playwright)
      |
      v
Cloud Storage (staging + archive)
      |
      v
Gmail API
      |
      v
HTML Attachment
      |
      v
User's Gmail / iPad
```

### 3.2 组件职责

| 组件 | 主要职责 | 不负责的事情 |
|---|---|---|
| OpenAI API | 研究、分析、写作、内容修订 | HTML 最终排版、邮件发送 |
| Markdown 协议 | 约束内容结构与媒体引用 | 视觉样式 |
| Python Orchestrator | 管理任务状态、调用各阶段 | 代替 LLM 写作 |
| Publication Engine | Markdown 转 HTML、模板渲染、资源封装 | 改写文章内容 |
| QA Engine | 检查内容、结构、视觉与技术质量 | 静默修复事实错误 |
| Cloud Storage | 暂存、归档输入与成品 | 作为用户主要阅读界面 |
| Gmail API | 发送附件、提供邮件 ID | 生成或修改日报 |
| Cloud Scheduler | 定时触发任务 | 判断文章质量 |

| 5.1.3 | **大模型 API 接口**。实现请求、响应解析和失败处理，将生成的正文、来源及媒体清单整理为现有引擎可接收的交稿包。 | 在测试配置下完成一次真实 API 调用，生成的稿件通过入库校验。记录调用失败和用量。 |
| 5.1.4 | **邮件投递组件**。以 Gmail 附件为交付目标，先明确授权、附件格式和发送结果核验方式，再实现发送接口及数据库回写。 | 用测试发送端检查收件人、附件和状态回写。已发送的任务跳过；首次发送结果不明时补发一次，正文说明实际故障、附件可能不完整，并请收件人核对两封邮件的附件。 |
| 5.1.5 | **单期流水线**。实现编排逻辑，依次完成期号登记与查重、模型产稿、文件入库、出版、质检、归档和投递。每一步记录结果和恢复位置。 | 一期样刊可走完整条本地流水线。质检失败时停止投递；投递失败后可复用已归档成品继续执行。 |
| 5.1.6 | **单期运行脚本与定时钩子脚本**。运行脚本按期号启动流水线；定时钩子计算目标期号并调用同一脚本。 | 手动运行与模拟定时触发均可启动任务。对同一期重复触发，用数据库记录验证只生产一次、只提交一次测试投递。 |

5.1 的完成依据是上述组件和本地联调记录。生产调度及凭证部署在 5.2 验收，真实邮箱收件与连续运行在 5.3 验收。以下是实施时需要核实的技术方向。

##### 5.1.1 事件去重与手动试做（2026-11-07）

**已确认的编辑规则**：按事件归集报道，逐条对照日报已经刊出的事实。同一事件换来源、换栏目或跨期出现，只要信息相同就跳过。有新事实时可以续写，重点交代这次增加了什么。

例如，昨天刊出“厂商自测准确率为 90%”。今天另一家媒体引用这组数字，跳过；独立实验室首次复测也得到 90%，可以续写。新增事实是该实验室亲自做了测试并得到相同结果。记录时保留测试主体与条件，以便读者判断两次结果是否可比。

**首期手动试做建议**：按下表整理材料，再依据实际样本决定数据库字段和关联方式。

| 记录层次 | 手动记录内容 |
|---|---|
| 事件 | 给同一件事一个稳定编号，附一句简述。跨期、跨栏目跟进时复用该编号。 |
| 已刊事实 | 每条写一个可以单独更新或纠正的陈述，保留主体、动作、对象以及影响含义的日期、数字、范围、状态。例如“已发布模型”和“计划开放 API”应分两条。 |
| 刊出依据 | 对每条事实记下期号、文章、修订、原文位置和来源。研究时看到、最终未写入日报的材料仍可在以后首次刊出。 |

选题时找到对应事件，将候选报道与已刊事实逐条比对，写下一句新增信息，并标记“跳过”或“续写”。下次从一期手动试做开始，保留判断实例。数据库选型、环境变量与部署步骤、模型接口与邮件实现、单期自动编排留待后续讨论。

##### 重要调研事项

不能假设 OpenAI API 自动拥有 ChatGPT 网页端相同的搜索和研究能力。必须验证：

- 可用模型与工具。
- Responses API 的搜索能力和调用方式。
- 如何保留来源 URL、标题和引用信息。
- 搜索失败与来源失效的处理。
- 如何控制研究深度和 Token 成本。
- 是否需要单独的搜索供应商。

##### API 费用原则

- 优先使用已激活且符合资格的 API Credits。
- 不默认启用无限额自动扣费。
- 每期统计输入、输出 Token 和工具调用费用。
- 为单期与月度成本设置预算阈值。
- 额度耗尽时暂停生产并通知，不自动扩大支出。

##### Gmail 技术方向

优先采用 Gmail API + Python，不采用浏览器 UI 自动点击作为正式发送方式。

建议附件参数：

```text

attachment
```

建议只申请：

```text

```

##### OAuth 风险

- 不将 OAuth 应用长期停留在 Testing 状态。
- 核实个人使用场景下的发布与验证要求。
- Refresh Token 放入 Secret Manager。
- 不将凭证写入代码仓库、Markdown、HTML 或日志。

##### 邮件发送状态

| 状态 | 意义 |
|---|---|
| `SEND_ACCEPTED` | Gmail API 接受发送请求并返回 Message ID |
| `SENT_VERIFIED` | 在 Gmail 已发送邮件中确认对应邮件和附件 |
| `DELIVERY_CONFIRMED` | 获得可靠投递证据；普通 Gmail API 本身不保证此状态 |

##### 重复发送保护

- 使用日期、内容版本和收件人生成唯一任务键。
- 保存 HTML SHA-256。
- 发送前检查当天是否已有相同邮件。
- 首次发送结果不明确时，使用同一份归档附件补发一次，并在正文说明原因和核验方法。
- 记录原发送和补发两次尝试。

```text
SCHEDULED
    ↓
RESEARCH
    ↓
WRITING
    ↓
CONTENT_VALIDATION
    ↓
PUBLISH
    ↓
HTML_QA
    ↓
ARCHIVE
    ↓
GMAIL_SEND
    ↓
DELIVERY_VERIFY
    ↓
COMPLETE
```

每个阶段保存独立状态、输入引用、输出文件、开始/结束时间、错误信息和重试次数。

失败恢复原则：

- 写作失败：只重试内容生产阶段。
- HTML 渲染失败：不重新调用 LLM。
- 浏览器质检失败：保留失败样本，不覆盖上一个有效成品。
- Gmail 发送失败：不重新生成正文和 HTML。
- 发送状态不明确：带说明补发一次。

## 6. 关键风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| API Credits 未激活或额度不足 | 内容生产停止 | 先核实资格与余额，设置预算阈值 |
| API 研究能力与 ChatGPT 不一致 | 内容质量下降 | 独立验证搜索工具和来源流程 |
| OAuth Refresh Token 失效 | Gmail 无法发送 | 正确配置 OAuth 发布状态，监控授权 |
| HTML 附件在 iPad 打开不便 | 最终阅读路径失败 | 提前进行真实设备测试 |
| 单文件图片过大 | 邮件附件超限 | 图片压缩、尺寸控制、体积检查 |
| 云端任务超时 | 日报未完成 | 分阶段执行、独立重试 |
| 重试造成重复邮件 | 用户收到重复日报 | 幂等键、Message ID、已发送核验 |
| 浏览器与本地预览不一致 | 视觉缺陷 | Playwright 真实浏览器验收 |
| 模板修改造成历史样式漂移 | 归档一致性受损 | 模板版本记录，历史成品不自动重写 |
| 云端服务成本不可控 | 产生额外费用 | API 与云资源分别设置预算和告警 |
