When the logs won’t fit in memory

At the 2 a.m. handover, the engineer on duty left a question for the next shift. A batch of requests had taken a long time to get a response the day before. Could we put the logs from several machines together and read the events in the order they happened? Every line on disk had a timestamp. The catch was that we had 120 GB of records and just 2 GB of memory available for sorting.

Normally we would load a batch of records, sort them by time and start looking for anomalies. The aim is the same at this scale. What changes is how much we can load at once. Follow these logs across the disk and we can see how a complete timeline takes shape in a fraction of the memory it would take to hold it.

Which record comes first?

The first line reads 10:17:03.412. So does the second. They came from different machines, both of which record time with millisecond precision. If we compare timestamps alone, either line can go first. Run the job again tomorrow and the two may swap places. Someone comparing the outputs line by line could easily conclude that a log had changed.

We keep two pieces of information with each record: the file it came from and the byte offset where it began. A fixed input list assigns each file a number. To compare two records, we first convert their timestamps to a common time zone. If the times match, we compare file numbers, then byte offsets. Every record now has a reproducible place in the timeline.

This convention settles the order on the page. If the clocks on two machines are three seconds apart, their entries will still be three seconds out of alignment. To work out which machine actually saw a request first, we need its request ID and the sequence of calls between services. With that distinction in mind, we can turn to the job of moving the records.

Writing sorted runs

Starting at the beginning of the first log, we read whole records into memory, sort the batch and write it sequentially to a temporary file. Then we clear the batch and read the next one. Each temporary file is internally sorted. We call it a run. The time ranges of two runs can still overlap: the last record in the first run might be hours later than the first record in the second.

Why not just read 2 GB from disk at a time? Once a line is in memory, the program also needs room for its parsed timestamp, its original location and an index pointing to the text. Sorting may need workspace of its own. What limits a batch is how much memory all of that occupies at once. The raw byte count is useful for tracking how far we have read.

There is a smaller boundary to watch, too. A read can end halfway through a line. We have to hold on to that fragment and join it to the bytes from the next read. Otherwise, the program might accept the first half as a message and reject the second half for lacking a timestamp. Bytes read and complete records delivered are two separate counts.

Look at the first record in each run

Take three short runs and keep only the minutes on the timestamps. Run A contains 02, 08 and 14. Run B contains 03, 04 and 12. Run C contains 01, 09 and 15. The three records in view are 02, 03 and 01. The earliest must be 01 from C: nothing further along in any run can be earlier than the record at its head.

After we write 01, only C advances, revealing 09. We now compare 02, 03 and 09 and write 02 from A. Next comes 03 from B. That exposes 04, which is earlier than both A’s 08 and C’s 09, so B supplies two records in succession. Each run advances at the pace set by its contents.

With many runs, scanning every head for each output record gets expensive. A common approach is to put the current candidate from each run into a min-heap. We remove the smallest candidate, write it out and replenish it from the same run. When a run ends, the heap has one fewer candidate. When the last candidate is written, the merge is finished. The heap needs just one entry per active run. The read buffers behind those entries can be allocated separately.

Counting disk traffic one pass at a time

Back to our 120 GB of logs. For an estimate we can check by hand, suppose the initial sort produces 120 equally sized runs, temporary records take up as many bytes as the originals and we can merge at most 16 runs at once. The first merge pass reduces 120 runs to eight: seven groups of 16 and one group of eight. All eight outputs fit into a single merge on the second pass.

Count reads and writes separately. Producing the initial runs takes 120 GB of reads and 120 GB of writes. The first merge pass reads all those runs and writes another 120 GB. The second pass reads and writes the same amount again. The final file is just 120 GB, but about 720 GB has crossed the disk interface. The same bytes may be compared many times in memory. For this estimate, each pass contributes one full read and one full write.

Now suppose we raise the number of runs we can merge at once from 16 to 32. The first merge pass produces four runs, and it still takes a second pass to combine them. We have fewer intermediate files but just as many full passes. To see whether the change pays off, time it on the actual device and record the buffer sizes. Halving the number of intermediate files does not halve the disk traffic.

Picking up after a power failure

Imagine the machine restarts halfway through writing the seventh group of the first merge pass. Six groups are complete. The output directory contains seven files, and their names tell us little about whether the last one is intact. Its first half may be perfectly sorted. Checking the first hundred records tells us only that those hundred are in order.

One approach is to write each group to a temporary path and record its input run IDs, the expected record count and the count actually written. After checking the output, we make it durable using the guarantees of the filesystem, then commit a completion marker. On restart we check which groups were committed and resume with the first unfinished group whose inputs are intact. We delete a group’s inputs only after the commit. That ordering determines where recovery can begin.

It also explains why free disk space deserves an estimate of its own. When a group’s output is nearly finished, its old inputs still have to be there. If we are retaining the original logs, they occupy space throughout the job as well. Total disk traffic tells us how much data has to move. Peak disk usage tells us how much must fit at one instant. One helps estimate the wait. The other helps determine whether the job can finish at all.

Reading the result one last time

Before handover, we can check the output in very little memory. Read the final file from the beginning, retaining only the previous sort key for comparison. If the next key is smaller, we can report the position of the inversion and the original locations of both records. At the end, compare the output count with the number of successfully parsed input records. List lines that failed to parse separately and keep their original text.

Both checks have limits. If one record is written twice and another is silently dropped, the count can match and the output can still be sorted. For a record-by-record completeness check, we can return to the original coordinates. For each input file, match the positions represented in the output against the positions recorded during the input scan. The coordinates that broke timestamp ties at the start now give us a way to audit the result.

Open the timeline around 10:17 again and those few seconds can finally be read straight through across machines. To find where a request queued and how long it took to show up on the next machine, we can follow its request ID. External merge sort has done its part: records scattered across many files can now be read in sequence, reproduced in the same order and traced back to the lines they came from.
